## پول و اعداد

**قانون طلایی:** هر عددی که پول، قیمت، حجم یا درصد سود است → `Decimal`.

```python
from decimal import Decimal

price = Decimal("62450.50")     # ✅ از رشته بساز
price = Decimal(62450.50)       # ❌ خطای float را وارد می‌کند
```

- `float` فقط برای چیزهای غیرمالی مجاز است (مثلاً درصد پیشرفت یک job).
- در دیتابیس: `NUMERIC(38, 18)`. هرگز `DOUBLE PRECISION`.
- در JSON: به‌صورت **رشته** سریالایز کن، نه عدد — وگرنه در جاوااسکریپت
  دقت از دست می‌رود. فرانت هم با کتابخانهٔ decimal کار کند.
- گرد کردن حجم **همیشه به سمت پایین** (`ROUND_DOWN`)، تا از موجودی بیشتر نشود.
- گرد کردن قیمت به دقت نماد، جهت بسته به side.

## زمان

- همه‌جا **UTC** و timezone-aware. `datetime.now(timezone.utc)`،
  هرگز `datetime.now()` یا `utcnow()`.
- در DB: `TIMESTAMPTZ`.
- تبدیل به وقت محلی فقط در لایهٔ نمایش (UI و پیام ربات).
- در کد استراتژی زمان **فقط** از `ctx.now` می‌آید.

## ساختار و نام‌گذاری

- ماژول‌ها و فایل‌ها: `snake_case.py`
- کلاس‌ها: `PascalCase` · توابع/متغیرها: `snake_case` · ثابت‌ها: `UPPER_SNAKE`
- هر پکیج یک `__init__.py` با export صریح.
- **type hint اجباری** روی هر تابع عمومی. `mypy` باید تمیز باشد.
- مدل‌های داده: `pydantic` برای مرز ورودی/خروجی (API، پاسخ صرافی)،
  `dataclass(frozen=True)` برای مدل‌های داخلی تغییرناپذیر.
- Enum برای هر مجموعهٔ محدود (`Side`, `OrderType`, `Mode`, ...) — نه رشتهٔ خام.

## خطاها {#errors}

سلسله‌مراتب خطای پروژه در `core/errors.py`:

```
DigiTradeError
├── ConfigError
├── ExchangeError
│   ├── ExchangeAuthError          # کلید/امضا اشتباه — retry نکن
│   ├── ExchangeRateLimitError     # با backoff retry کن
│   ├── ExchangeNetworkError       # retry کن (فقط خواندنی)
│   ├── InsufficientBalanceError   # retry نکن
│   └── InvalidOrderError          # دقت/حداقل حجم — retry نکن
├── StrategyError
├── RiskRejectedError              # سیگنال رد شد؛ خطا نیست، تصمیم است
└── BotError
```

**قوانین:**
- خطای خام کتابخانهٔ خارجی (`httpx.HTTPError`, `asyncpg.*`) نباید از لایهٔ
  خودش بیرون نشت کند. در مرز، wrap شود.
- `except Exception: pass` ممنوع. اگر واقعاً باید بلعیده شود، لاگ `warning`
  با دلیل صریح.
- خطای مرتبط با پول یا سفارش هرگز بی‌صدا نماند — لاگ `error` + اعلان.

## لاگ

- `structlog` با خروجی JSON در production، خوانا در development.
- هر لاگ مرتبط با معامله این فیلدها را داشته باشد:
  `exchange`, `symbol`, `strategy_run_id`, `client_order_id`, `mode`, `target`
- سطوح:
  - `debug` — جریان داده، پیام‌های WS
  - `info` — سیگنال، ارسال سفارش، پر شدن، گذار حالت
  - `warning` — retry، reconnect، سیگنال ردشده
  - `error` — شکست سفارش، خطای امضا، کرش task
- **هرگز لاگ نکن:** کلید API، secret، توکن ربات، هدر امضا.
  یک فیلتر در پیکربندی لاگ بگذار که این کلیدها را ماسک کند.

- `pydantic-settings` در `core/config.py`، تنها منبع خواندن env.
- `os.environ` مستقیم در هیچ‌جای دیگری استفاده نشود.
- `.env` در `.gitignore`. `.env.example` با کلیدها و مقادیر خالی کامیت شود.
- قبل از هر `git add`، `git status` را بخوان. اگر فایلی مشکوک بود،
  محتوایش را ببین.
- `SecretStr` برای هر مقدار حساس، تا در `repr` نشت نکند.

### کلیدهای صرافی (تصمیم D10)

**کلید API صرافی در `.env` نیست.** فقط این‌ها در env می‌مانند:

```
DIGITRADE_MASTER_KEY   # کلید AES-GCM، تنها ریشهٔ اعتماد
DATABASE_URL
REDIS_URL
TELEGRAM_BOT_TOKEN
BALE_BOT_TOKEN
BOOTSTRAP_REGISTRATION_TOKEN   # یک‌بارمصرف، بعد از اولین ثبت باطل می‌شود
```

کلید و سکرت صرافی با `core/crypto.py` رمز می‌شوند و در
`exchange_credentials` می‌نشینند. قوانین:

- رمزگشایی فقط در لحظهٔ ساخت کلاینت صرافی، در حافظه. هیچ‌جا کش نشود روی دیسک.
- `api_secret` هرگز از API بک‌اند برنگردد — حتی برای admin. فقط ۴ کاراکتر
  آخر `api_key` برای شناسایی نمایش داده شود.
- **کلید API صرافی هرگز مجوز برداشت نگیرد.** موقع ساخت کلید در پنل صرافی:
  فقط `read` + `trade`. اگر صرافی IP allowlist دارد، IP سرور را قفل کن.
- چرخش کلید باید از UI ممکن باشد و در `audit_log` ثبت شود.
- اگر `DIGITRADE_MASTER_KEY` گم شود، همهٔ credentialها غیرقابل‌بازیابی‌اند —
  این را در مستندات دیپلوی بنویس.

## تست

- `pytest` + `pytest-asyncio`. تست‌ها در `backend/tests/` هم‌ساختار با `app/`.
- **هیچ تستی به شبکهٔ واقعی نزند.** HTTP با `respx` mock شود.
- برای هر کلاینت صرافی: پاسخ‌های واقعی را یک بار ضبط کن و به‌عنوان
  fixture نگه‌دار — تست‌ها روی همان اجرا شوند.
- تست‌های اجباری قبل از هر کامیت روی مسیر پول:
  - گرد کردن دقت قیمت/حجم
  - محاسبهٔ پوزیشن‌سایز
  - هر قانون `RiskManager`
  - گذارهای `PositionStateMachine`
  - idempotency ارسال سفارش
  - نبود look-ahead در بک‌تست
- تست را برای سبز شدن CI اسکیپ یا حذف نکن.
