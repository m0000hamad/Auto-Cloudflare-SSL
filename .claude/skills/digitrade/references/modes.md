# DigiTrade — مودها، موتور استراتژی و مدیریت ریسک

## دو محور مستقل

اشتباه رایج این است که «پیپر/لایو» و «دستی/خودکار» را یک چیز بدانیم.
این‌ها دو محور جدا هستند و هر ترکیبی از آن‌ها معتبر است:

### محور ۱ — مقصد اجرا (Execution Target)

| مقدار | یعنی |
|---|---|
| `paper` | سفارش به `PaperBroker` می‌رود، پول واقعی درگیر نیست. **پیش‌فرض همیشه** |
| `live` | سفارش واقعی به صرافی می‌رود |

### محور ۲ — مود تصمیم‌گیری (Decision Mode)

| مقدار | یعنی |
|---|---|
| `signal_only` | استراتژی سیگنال می‌دهد، **هیچ سفارشی نمی‌رود**. فقط اعلان به تلگرام/بله و UI |
| `manual_confirm` | سیگنال با دکمهٔ «تأیید / رد» فرستاده می‌شود؛ فقط با تأیید کاربر اجرا می‌شود |
| `semi_auto` | خودکار اجرا می‌شود، ولی اعلان **قبل از** اجرا فرستاده می‌شود و کاربر پنجرهٔ کوتاهی برای وتو دارد |
| `full_auto` | خودکار و بی‌مکث اجرا می‌شود؛ اعلان بعد از اجرا |

به‌علاوه `manual` که اصلاً استراتژی درگیر نیست و کاربر خودش از UI یا ربات
سفارش می‌گذارد.

**ترکیب‌های پرکاربرد:**
- `paper` + `full_auto` → تست استراتژی روی بازار زنده بدون ریسک
- `live` + `manual_confirm` → حالت محافظه‌کارانهٔ شروع
- `live` + `signal_only` → فقط مشاوره؛ کاربر خودش دستی معامله می‌کند
- `live` + `full_auto` → حالت نهایی، فقط بعد از اعتماد کامل

### قانون گذار به live

رفتن از `paper` به `live` نیازمند:
1. درخواست صریح کاربر (نه استنباط از متن)
2. تأیید دوم در UI/ربات («مطمئنی؟»)
3. ثبت در `audit_log` با `actor` و `source`
4. نمایش دائمی و پررنگ در UI و در پانویس هر پیام ربات

هیچ کد، migration، یا مقدار پیش‌فرضی نباید `live` را فعال کند.

## ماشین حالت پوزیشن

```
       ┌──────────┐
       │  FLAT    │◄──────────────────┐
       └────┬─────┘                   │
            │ سیگنال ورود تأیید شد    │
       ┌────▼─────┐                   │
       │ OPENING  │──── رد/لغو شد ────┤
       └────┬─────┘                   │
            │ سفارش پر شد             │
       ┌────▼─────┐                   │
       │   OPEN   │                   │
       └────┬─────┘                   │
            │ TP / SL / سیگنال خروج / دستور دستی
       ┌────▼─────┐                   │
       │ CLOSING  │                   │
       └────┬─────┘                   │
            │ خروج پر شد              │
       ┌────▼─────┐                   │
       │  CLOSED  │───────────────────┘
       └──────────┘
```

**قوانین:**
- گذارها فقط از طریق `PositionStateMachine` انجام شود، نه با `UPDATE` مستقیم.
- هر گذار در `audit_log` ثبت شود.
- در حالت `OPENING` و `CLOSING`، سیگنال جدید روی همان نماد **نادیده گرفته
  می‌شود** (نه صف‌بندی) و دلیلش لاگ می‌شود.
- قفل per-symbol هنگام گذار الزامی است.

## نوشتن استراتژی

```python
class Signal(NamedTuple):
    action: Action          # ENTER_LONG | ENTER_SHORT | EXIT | HOLD
    strength: Decimal       # 0..1 — برای پوزیشن‌سایزینگ
    reason: str             # متن قابل‌نمایش به کاربر در ربات
    stop_loss: Decimal | None
    take_profit: Decimal | None
```

قوانین سفت:

1. **`on_candle` خالص است.** بدون شبکه، بدون DB، بدون `datetime.now()`.
   زمان از `ctx.now`، داده از `ctx.candles`.
2. **فقط کندل بسته.** `ctx.candles[-1]` آخرین کندل **بسته‌شده** است.
   کندل در حال شکل‌گیری هرگز به استراتژی داده نمی‌شود.
3. **`warmup_bars()` را درست برگردان.** اگر EMA200 داری، عدد باید ≥ ۲۰۰ باشد.
   موتور تا قبل از پر شدن warmup هیچ سیگنالی را قبول نمی‌کند.
4. **`reason` را پر کن.** کاربر در تلگرام باید بفهمد چرا این سیگنال آمده.
   «RSI(14)=28.4 زیر ۳۰ + قیمت بالای EMA200» نه «شرایط ورود برقرار است».
5. **پارامترها در `params`.** هیچ عدد جادویی داخل بدنهٔ منطق نباشد،
   وگرنه بهینه‌سازی و بک‌تست پارامتری غیرممکن می‌شود.

برای منطق اندیکاتورها و طراحی استراتژی از اسکیل `trading-skill` استفاده کن.

## RiskManager

قبل از هر اجرا، این بررسی‌ها انجام می‌شود. هر کدام رد شود، سیگنال
`rejected` می‌شود و دلیلش به کاربر اعلام می‌شود:

| بررسی | پیش‌فرض پیشنهادی |
|---|---|
| حداکثر ریسک هر معامله (٪ سرمایه) | ۱٪ |
| حداکثر تعداد پوزیشن باز همزمان | ۳ |
| حداکثر پوزیشن باز روی یک نماد | ۱ |
| حداکثر دراودان روزانه → توقف کامل | ۵٪ |
| حداکثر تعداد معاملهٔ روزانه | ۱۰ |
| حداقل فاصله بین دو ورود روی یک نماد | ۱ کندل |
| بررسی `min_notional` و موجودی | همیشه |

**Kill switch:** یک پرچم سراسری که با یک دستور از UI یا ربات (`/stop`)
همهٔ اجراهای خودکار را متوقف می‌کند و هیچ سفارش جدیدی نمی‌گذارد.
پوزیشن‌های باز را نمی‌بندد (آن دستور جداست: `/closeall`).

پوزیشن‌سایزینگ بر اساس ریسک محاسبه می‌شود، نه درصد ثابت سرمایه:

```
risk_amount = equity × risk_per_trade
distance    = |entry_price − stop_loss|
amount      = risk_amount / distance
```

اگر استراتژی `stop_loss` نداده باشد، از `default_stop_pct` استفاده کن —
و اگر آن هم نبود، سیگنال را رد کن. **پوزیشن بدون حد ضرر باز نمی‌شود.**

## پیکربندی مودها

هر `strategy_run` مود خودش را دارد؛ مود سراسری نداریم. یعنی می‌شود همزمان
یک استراتژی در `live/full_auto` روی BTC و یکی در `paper/signal_only` روی ETH
داشت. `ModeResolver` مود مؤثر را از رکورد `strategy_runs` می‌خواند، نه از
تنظیمات سراسری.

استثنا: kill switch سراسری است و بر همه چیز اولویت دارد.
