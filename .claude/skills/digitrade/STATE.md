## قدم بعدی

> نشست بعد دقیقاً از اینجا شروع کن.

**۱. ساختار ریپو را بساز** (فاز ۰)

```
backend/
  app/
    core/          # config, logging, errors, decimal helpers
    exchanges/
      base.py      # ExchangeClient ABC — قرارداد مشترک
      coinex/
      lbank/
    marketdata/    # ingest, normalize, candle store
    strategy/      # Strategy ABC + built-ins
    engine/        # live engine + backtest engine (کد استراتژی مشترک)
    execution/     # order router, paper broker, position state machine
    bots/
      base.py      # BotTransport ABC
      telegram/
      bale/
    api/           # FastAPI routers + WebSocket
    db/            # models, migrations (alembic)
  tests/
frontend/
docs/
```

**۲. `backend/app/core/config.py`** با pydantic-settings + `.env.example`
(بدون هیچ مقدار واقعی) — طبق خط قرمز شمارهٔ ۱ در SKILL.md.
تنها سکرت‌های env: `DIGITRADE_MASTER_KEY`، `DATABASE_URL`، `REDIS_URL`،
توکن ربات‌ها، و توکن ثبت‌نام یک‌بارمصرف. کلید صرافی‌ها **در env نیست** (D10).

**۳. `backend/app/core/crypto.py`** — رمزنگاری/رمزگشایی AES-GCM با master key،
برای جدول `exchange_credentials`. قبل از فاز ۱ لازم است.

**۴. اسکیمای اولیهٔ دیتابیس** روی Neon: جدول‌های
`exchanges`, `exchange_credentials`, `symbols`, `candles`, `funding_rates`,
`strategies`, `strategy_runs`, `signals`, `orders`, `positions`,
`position_events`, `backtests`, `backtest_trades`, `bot_users`, `audit_log`.
قبل از نوشتن، `references/architecture.md#data-model` را بخوان —
فیلدهای فیوچرز (اهرم، مارجین، لیکوئید، funding) **اجباری‌اند نه اختیاری**.

**۵. `backend/app/exchanges/base.py`** — تعریف `ExchangeClient` ABC با
متدهای فیوچرز: `fetch_positions`, `set_leverage`, `set_margin_mode`,
`fetch_mark_price`, `fetch_funding_rate`, `watch_positions`.
این قرارداد قبل از نوشتن هر کلاینت واقعی باید قفل شود، وگرنه
CoinEx و LBank دو شکل متفاوت درمی‌آیند.

**۶. `backend/app/execution/liquidation.py`** — محاسبهٔ قیمت لیکوئیدیشن
و فاصلهٔ تا آن. این ماژول قبل از هر کد اجرایی لازم است، چون `RiskManager`
بدون آن نمی‌تواند تصمیم بگیرد (D20).

## تصمیمات قفل‌شده

تصمیماتی که گرفته شده‌اند و بدون دلیل جدید تغییر نمی‌کنند:

| # | تصمیم | دلیل |
|---|---|---|
| D1 | بک‌اند Python + FastAPI + asyncio | اکوسیستم تحلیل داده و اندیکاتور؛ WS همزمان چند صرافی |
| D2 | کلاینت صرافی اختصاصی، نه اتکای کامل به ccxt | امضای CoinEx و LBank خاص است؛ WS آن‌ها در ccxt ناقص/کند به‌روز می‌شود. ccxt فقط به‌عنوان مرجع تطبیق مجاز است |
| D3 | یک کلاس استراتژی، دو موتور اجرا (live/backtest) | جلوگیری از واگرایی منطق بین بک‌تست و لایو |
| D4 | `Decimal` برای همهٔ اعداد پولی | خطای شناور در حجم/قیمت غیرقابل‌قبول است |
| D5 | پیش‌فرض همهٔ محیط‌ها `paper` | ارسال سفارش واقعی باید تصمیم صریح کاربر باشد |
| D6 | تلگرام و بله پشت یک اینترفیس مشترک `BotTransport` | API بله عمداً سازگار با تلگرام است؛ کد دوباره نوشته نشود |
| D7 | PostgreSQL روی Neon به‌عنوان دیتابیس اصلی | کانکتور Neon از قبل وصل و فعال است |
| D8 | زبان گفتگو فارسی، زبان کد/کامیت انگلیسی | ترجیح کاربر + خوانایی کد |
| D9 | ~~اسپات اول~~ → **فیوچرز، بازار اصلی پروژه** (بازنگری نشست ۳) | خواستهٔ کاربر. اسپات حذف نمی‌شود ولی اولویت دوم است و بعد از پایدار شدن فیوچرز اضافه می‌شود. `market_type` در اسکیما می‌ماند، ولی مسیر اصلی `futures` است نه `spot` |
| D10 | **کلیدهای صرافی رمزنگاری‌شده در DB، نه خام در `.env`** | فقط یک master key در env می‌ماند (`DIGITRADE_MASTER_KEY`)؛ credentialها با AES-GCM رمز و در جدول `exchange_credentials` ذخیره می‌شوند. مزیت: چند حساب، چرخش کلید از UI، و dump دیتابیس به‌تنهایی کلید لو نمی‌دهد. **کلید API صرافی هرگز مجوز برداشت (withdrawal) نگیرد** — فقط read + trade، و در صورت پشتیبانی، IP allowlist |
| D11 | **دیپلوی روی VPS خارج از ایران** | CoinEx و LBank برای IP ایران بلاک/محدود می‌کنند و تلگرام هم فیلتر است. بله از خارج در دسترس است، پس VPS خارجی هر سه را حل می‌کند. چون استراتژی‌ها کندل‌محورند (دقیقه‌ای)، تأخیر ۱۰۰–۳۰۰ms بی‌اهمیت است → انتخاب بر اساس پایداری و قیمت، نه لتنسی. یک لایهٔ پیکربندی proxy خروجی اختیاری هم باشد تا محل دیپلوی hardcode نشود |
| D12 | **شروع با BTC/USDT و ETH/USDT، ولی watchlist از ابتدا پیکربندی‌پذیر** | این دو در **هر دو** صرافی لیست‌اند (تست لایهٔ چندصرافی + مقایسهٔ قیمت)، بیشترین نقدشوندگی را دارند (اسپرد کم → بک‌تست واقع‌گراتر)، و طولانی‌ترین تاریخچهٔ تمیز را. هیچ نمادی در کد hardcode نشود |
| D13 | **تک‌مستأجر، چندکاربره** | یک حساب معاملاتی، چند نفر با نقش (viewer/trader/admin). SaaS چندمستأجری نیست — این تصمیم لایهٔ auth و مدل داده را ساده نگه می‌دارد |
| D14 | **تایم‌فریم‌های شروع: ۵m، ۱۵m، ۱h، ۴h** | زیر ۱ دقیقه مسئلهٔ مهندسی متفاوتی است (نیاز به tick data و لتنسی واقعاً مهم می‌شود)؛ روزانه برای اعتبارسنجی استراتژی خیلی کند است |
| D15 | **فقط پرپچوال USDT-margined** (نه coin-margined، نه delivery) | نقدشونده‌ترین و ساده‌ترین. مارجین، PnL و ریسک همه به USDT است — بدون لایهٔ تبدیل ارز. coin-margined ریسک را غیرخطی می‌کند (وثیقه‌ات همان چیزی است که روش پوزیشن داری) |
| D16 | **مارجین ایزوله، نه کراس** | در ایزوله شعاع انفجار هر پوزیشن محدود به مارجین خودش است. در کراس یک پوزیشن بد می‌تواند کل حساب را ببرد. برای سیستم خودکار، مهار خسارت از بهینگی سرمایه مهم‌تر است |
| D17 | **حالت پوزیشن one-way، نه hedge** | hedge mode ماشین حالت را دو برابر می‌کند و برای استراتژی سیستماتیک تک‌جهته سودی ندارد. لانگ و شورت همزمان روی یک نماد ممنوع |
| D18 | **سقف اهرم نرم‌افزاری، مستقل از سقف صرافی** | صرافی تا ۱۰۰x می‌دهد؛ ما در پیکربندی سقف می‌گذاریم (پیش‌فرض **۳x**، حداکثر مجاز ۵x). اهرم بالا فاصلهٔ تا لیکوئید را آن‌قدر کم می‌کند که نویز عادی بازار پوزیشن را می‌بندد |
| D19 | **قیمت mark مبنای لیکوئیدیشن و PnL شناور؛ قیمت last مبنای سیگنال** | صرافی لیکوئید را با mark حساب می‌کند نه last. اگر ما با last حساب کنیم، تخمین فاصلهٔ تا لیکوئید غلط می‌شود — دقیقاً در بدترین لحظه |
| D20 | **حد ضرر همیشه قبل از قیمت لیکوئیدیشن، با حاشیه** | اگر SL آن‌طرف لیکوئید باشد عملاً وجود ندارد. `RiskManager` این را چک می‌کند و یا اهرم را کم می‌کند یا سیگنال را رد |
